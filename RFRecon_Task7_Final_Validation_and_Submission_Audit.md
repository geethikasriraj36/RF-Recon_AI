\## 3. Feature Extraction Validation



The shared feature schema contains ten features:



1\. `mean\_power`

2\. `rms`

3\. `peak\_amplitude`

4\. `variance`

5\. `peak\_frequency\_normalized`

6\. `spectral\_centroid\_normalized`

7\. `spectral\_bandwidth\_normalized`

8\. `occupied\_bandwidth\_normalized`

9\. `spectral\_flatness`

10\. `peak\_to\_average\_ratio`



Previous source and numerical audits found differences between the shared extractor, synthetic training pipeline, real Wi-Fi feature generator, and final inference implementation.



Before claiming final validation:



\- Use one canonical feature extractor for training and inference.

\- Verify the feature count and exact feature order.

\- Compare the calculated feature values on identical IQ windows.

\- Confirm finite values and expected numeric types.

\- Record the extractor version and sample-rate configuration.



Matching feature names alone do not prove formula compatibility.



\## 4. Dataset and Label Validation



The inspected hybrid dataset contains 2,400 rows:



| Class label | Rows |

|---|---:|

| `noise` | 500 |

| `bluetooth\_like` | 500 |

| `zigbee\_like` | 500 |

| `cellular\_like` | 500 |

| `wifi\_like` | 400 |



The hybrid dataset combines synthetic examples with real Wi-Fi feature rows. These row counts do not imply equal provenance or equal real-world validation across classes.



Before submission:



\- Record the origin of every dataset and derived feature table.

\- Distinguish synthetic data from real captures.

\- Preserve source capture identifiers.

\- Verify labels against appropriate evidence.

\- Document missing or uncertain metadata.

\- Avoid presenting candidate or synthetic labels as independently verified ground truth.



\## 5. Acquisition Metadata Limitations



The inspected cellular capture records contain a discrepancy between a configured center frequency of 1.872 GHz and a metadata value of 1.856 GHz. The actual acquisition setting remains unverified.



The inspected IEEE 802.15.4/6LoWPAN-related data comes from one capture. The available evidence does not establish verified Zigbee application traffic, and the associated PCAP's structural validity does not prove that its packets correspond to the IQ recording.



These limitations must remain visible in the final submission. Do not silently select a frequency value or claim verified Zigbee data without additional evidence.



\## 6. Model Evaluation Requirements



The inspected training scripts use stratified random row-level splits. Such splits may place windows from the same capture in both training and test sets.



Where enough independent captures exist, use capture-aware splitting to evaluate generalization to unseen captures.



The final results should include:



\- Overall accuracy.

\- Per-class precision, recall, and F1-score.

\- Macro-average F1-score.

\- Confusion matrix.

\- Test sample count for each class.

\- Number of independent source captures per class.

\- Split method, seed, and configuration.

\- Feature extraction and preprocessing details.



No new model metrics were generated by this audit. Include only metrics produced by an actual, reproducible evaluation run.



\## 7. Integration and Reproducibility Checks



Before running the full pipeline, confirm that:



\- Input paths and output paths are understood.

\- Existing datasets, models, and reports will not be overwritten.

\- Model files match the intended feature schema.

\- Input validation catches short, invalid, or non-finite IQ data.

\- Sample rate and other required metadata are checked.

\- Test outputs are written to a controlled location.

Several inspected scripts perform file operations at top level. Do not import or execute them for validation until their side effects and output paths have been reviewed.
