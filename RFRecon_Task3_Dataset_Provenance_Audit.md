\# RFRecon\_AI — Task 3: Dataset Provenance Audit



\## 1. Objective



This audit documents the provenance, labeling, acquisition metadata, and limitations of the datasets used by RFRecon\_AI. It distinguishes real captures, synthetic training data, derived feature datasets, and unverified candidate data.



The audit is based on existing source files, dataset inspections, and collection records. It does not establish independently verified ground truth where acquisition metadata or capture provenance is incomplete.



\## 2. Dataset Categories



The project contains several distinct data categories:



\- Synthetic IQ signals generated by project scripts.

\- Real Wi-Fi feature windows derived from captured IQ data.

\- Real Bluetooth-like and noise capture feature datasets.

\- Candidate cellular IQ captures and derived feature datasets.

\- IEEE 802.15.4/6LoWPAN-related capture material.

\- Combined training and evaluation datasets derived from these sources.



These categories should remain distinguishable in dataset metadata and evaluation reports. A derived feature CSV is not an independent capture, and multiple windows from one capture do not represent multiple independent acquisition sessions.



\## 3. Synthetic Training Data



`generate\_robust\_training.py` generates synthetic IQ examples and saves signals as `.npy` files. Its signal-generation functions include a normalization step that rescales signals toward unit average power.



`prepare\_robust\_dataset.py` subsequently computes feature rows for the robust training dataset.



The synthetic data is useful for prototyping and controlled experiments. It must not be described as real RF capture data or independently verified ground truth.



Because synthetic signals are normalized while real Wi-Fi examples retain substantially lower measured power levels in the inspected hybrid dataset, a distribution mismatch is possible. Its effect on classification must be established through controlled evaluation rather than assumed.



\## 4. Real Wi-Fi Data



The inspected `real\_wifi\_dataset` contains IQ windows used to generate `real\_wifi\_dataset.csv`.



A read-only check of `real\_wifi\_dataset/real\_wifi\_0000.npy` found:



\- Shape: 4,096 samples

\- Data type: `complex64`

\- Complex IQ: yes

\- Finite sample values: yes



The feature comparison on this window found that five of ten features matched the shared extractor within the comparison tolerance, while five differed.



This result applies to the inspected window only. It does not establish consistency across every Wi-Fi window or prove the accuracy of the final classifier.



The project also references `real\_wifi\_capture\_03.dat` in the final inference pipeline. Its use by that pipeline does not by itself establish that it is an independent capture from the training dataset.



\## 5. Existing Real-Capture Feature Dataset



The inspected `real\_dataset/real\_capture\_features\_consistent.csv` contains 500 feature windows for each of three labels:



\- `bluetooth\_like`, associated with `real\_bluetooth\_01.dat`

\- `noise`, associated with `real\_noise\_01.dat`

\- `wifi\_like`, associated with `real\_wifi\_01.dat`



Each of these classes is represented by one source capture in the inspected dataset.



Consequently, the 500 windows per class must not be interpreted as 500 independent captures. A capture-aware train/test split for these classes is not possible using only one capture per class.



The collection records do not fully establish all acquisition settings for these captures. Sample rate, center frequency, gain, and other metadata should be treated as unverified wherever the records do not confirm the actual settings.



\## 6. Cellular Capture Provenance



The collection records identify `real\_cellular\_01.dat` as a candidate cellular capture.



The inspected file size was 1,119,092,736 bytes. If interpreted as `complex64` IQ samples, this corresponds to 139,886,592 complex samples. At an assumed sample rate of 20 MS/s, the corresponding duration is approximately 6.99 seconds.



These calculations are conditional on the assumed sample format and sample rate; they do not independently verify the capture format or acquisition configuration.



A metadata discrepancy remains unresolved:



\- The flowgraph configuration references a center frequency of 1.872 GHz.

\- The collection metadata records 1.856 GHz.

\- The actual acquisition settings have not been independently confirmed.



Therefore, the capture should remain labeled as a candidate cellular capture until its acquisition metadata and signal characteristics are verified. The discrepancy must not be silently resolved by choosing one value.



The inspected `real\_dataset/real\_cellular\_dataset.csv` contains metadata using the 20 MS/s sample rate and 1.856 GHz center-frequency value. This is not independent confirmation of the actual receiver settings.



The separate `real\_cellular\_scan\_01.dat` capture was also identified in the collection records, with incomplete acquisition-condition documentation.



\## 7. IEEE 802.15.4 / 6LoWPAN-Related Material



The project contains `real\_dataset/6lowpan\_ping.dat`, with a recorded file size of 317,864,640 bytes.



If interpreted as `complex64`, the file contains 39,733,080 complex samples. The associated flowgraph defaults indicate 4 MS/s and 2.415 GHz, but the actual acquisition settings have not been independently confirmed.



The project has extracted 500 feature windows from a single capture. This does not establish independent-capture validation.



The associated `6lowpan\_ping.pcap` was inspected as a structurally valid PCAP v2.4 file with link type 195, IEEE 802.15.4 with FCS. It contains 14 records, each 125 bytes, spanning approximately 6.01492 seconds.



The PCAP's structural validity does not prove that its packets correspond to the recorded IQ samples.



The label `ieee802154\_6lowpan` should not be treated as verified Zigbee application traffic without additional protocol-level evidence. IEEE 802.15.4, 6LoWPAN, and Zigbee are related but not interchangeable labels.



\## 8. BLE and Zigbee Candidate Archive



The inspected `zigbee\_ble\_dataset.zip` contains 123 Zigbee-named `.sigmf` containers whose associated `.sigmf-data` files are empty. The inspected CSV files are header-only, and the metadata describes BLE advertising.



On the inspected evidence, this archive does not provide usable Zigbee IQ samples for validated feature extraction. Its filenames and metadata labels are not sufficient to establish that it contains usable Zigbee captures.



The archive should not be counted as a verified Zigbee dataset unless usable IQ samples and consistent acquisition/protocol metadata are obtained.



\## 9. Hybrid Dataset Lineage



The inspected `hybrid\_training\_dataset.csv` contains 2,400 rows:



| Label | Rows |

|---|---:|

| `noise` | 500 |

| `bluetooth\_like` | 500 |

| `zigbee\_like` | 500 |

| `cellular\_like` | 500 |

| `wifi\_like` | 400 |



The inspected feature columns contained no missing values, and populated `class\_name` values agreed with `label`.



The hybrid dataset combines synthetic class examples with real Wi-Fi feature rows. The row counts do not establish that all five classes have equivalent provenance or verified real-world ground truth.



The dataset construction script uses 400 real Wi-Fi rows for training and reserves 100 other real Wi-Fi rows in `real\_wifi\_test\_dataset.csv`. This division separates rows, but the source capture relationship must be considered when interpreting independence and generalization.



\## 10. Metadata and Labeling Recommendations



For every capture and derived feature row, preserve the following fields when available:



\- Source capture identifier and source filename

\- Data origin: synthetic, real capture, or derived dataset

\- Class label and labeling method

\- Sample format and data type

\- Actual sample rate and center frequency, including verification status

\- Receiver gain and relevant acquisition settings

\- Window length, stride, and feature extractor version

\- Capture session or acquisition identifier

\- Any unresolved discrepancies or uncertainty



Unknown values should remain explicitly unknown rather than being silently filled from configuration defaults.



Candidate labels should be distinguished from verified labels. The provenance of each derived CSV should be traceable back to its source capture or synthetic generator.



\## 11. Limitations



This audit does not independently verify the RF origin of every capture, confirm all receiver settings, validate the association between the PCAP and IQ data, or establish ground truth for candidate cellular and Zigbee-related classes.



It also does not provide new model accuracy measurements. Provenance and feature consistency are prerequisites for interpreting such measurements, not substitutes for them.



\## 12. Conclusion



The inspected project contains a mixture of synthetic data, real-capture-derived features, candidate captures, and protocol-related material with unresolved provenance.



The most important limitations are the unresolved cellular center-frequency discrepancy, incomplete acquisition metadata, one-capture-per-class limitations for the inspected real-capture feature dataset, and the absence of usable verified Zigbee IQ in the inspected candidate archive.



RFRecon\_AI should retain these distinctions in training, testing, documentation, and presentation. Strong claims about real-world classification should follow verified acquisition metadata, traceable labels, and evaluation on independent captures.

\*\*Scope note:\*\* This report records the inspected evidence and its limitations. It does not claim that unverified candidate captures constitute validated ground truth.
